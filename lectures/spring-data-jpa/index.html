02 // OBJECT–RELATIONAL MAPPING

ORM tłumaczy między dwoma różnymi modelami

Świat obiektowy

  • tożsamość obiektu i referencje,
  • dziedziczenie i kolekcje,
  • graf obiektów w pamięci.

Świat relacyjny

  • klucze główne i obce,
  • wiersze, kolumny i złączenia,
  • ograniczenia oraz transakcje.
ORM nie usuwa SQL-a. Generuje go na podstawie mapowania i nadal wymaga rozumienia modelu relacyjnego.

08 // KLASA ↔ TABELA

Encja ma tożsamość i mapowanie

Book.java
@Entity
@Table(name = "books")
public class Book {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  @Column(nullable = false, length = 200)
  private String title;

  protected Book() { }
}
KONTRAKT JPA

Konstruktor bezargumentowy

Musi być co najmniej protected. Encja nie powinna być rekordem ani klasą final, ponieważ provider może korzystać z proxy.

12 // MAPOWANIE KLUCZA OBCEGO

@ManyToOne wskazuje stronę posiadającą relację

Book.java / Author.java
// Book
@ManyToOne(fetch = FetchType.LAZY,
           optional = false)
@JoinColumn(name = "author_id")
private Author author;

// Author
@OneToMany(mappedBy = "author")
private final List<Book> books =
    new ArrayList<>();
OWNING SIDE

Book.author kontroluje FK

mappedBy wskazuje pole po drugiej stronie. W kodzie domenowym warto synchronizować obie strony metodą, np. author.addBook(book).

13 // SKĄD BIERZE SIĘ N+1

Zapytanie pobiera encje główne, ale nie ich relacje

Repozytorium wykonuje jedno zapytanie po listę autorów. Kolekcja Author.books jest oznaczona jako LAZY, więc początkowo zawiera tylko proxy — obietnicę pobrania danych później.

Moment wyzwalający: pierwsze użycie kolekcji każdego autora powoduje osobne zapytanie SQL.
MECHANIZM
findAll()lista autorów
›
books = proxyjeszcze bez danych
›
getBooks()dodatkowy SELECT
Ważne: samo LAZY nie jest błędem. Problem powstaje, gdy kod przechodzi po wielu encjach i dla każdej osobno inicjalizuje relację.
13A // KONKRETNY PRZYKŁAD

Trzech autorów oznacza cztery zapytania

LibraryService.java
@Transactional(readOnly = true)
public void printBooks() {
  List<Author> authors = repository.findAll();

  for (Author author : authors) {
    System.out.println(author.getBooks().size());
  }
}
SQL wygenerowany przez Hibernate
-- 1 zapytanie główne
SELECT * FROM authors;

-- N zapytań: po jednym dla każdego autora
SELECT * FROM books WHERE author_id = 1;
SELECT * FROM books WHERE author_id = 2;
SELECT * FROM books WHERE author_id = 3;
1pobranie wszystkich autorów
+3inicjalizacja trzech kolekcji
=4zapytania zamiast jednego
13B // JAK USUNĄĆ N+1

Plan pobierania trzeba dopasować do przypadku użycia

JOIN FETCH

Jawne JPQL

select distinct a from Author a left join fetch a.books

Jedno zapytanie pobiera autorów razem z książkami.

@EntityGraph

Plan na metodzie

@EntityGraph(attributePaths = "books")

Repozytorium deklaruje relacje potrzebne w tej operacji.

DTO projection

Tylko potrzebne dane

Zapytanie zwraca płaską projekcję dopasowaną do widoku.

Nie buduje całego grafu encji.

Nie naprawiaj przez globalne EAGER. Może ono pobierać relacje także tam, gdzie nie są potrzebne, a przy niektórych zapytaniach nadal prowadzić do dodatkowych SELECT-ów.
Jak wykryć: włącz logowanie SQL, policz zapytania i obserwuj, czy ich liczba rośnie wraz z liczbą rekordów wynikowych.

19 // JAWNE JPQL

@Query umieszcza zapytanie przy metodzie repozytorium

BookRepository.java
@Query("""
  select b from Book b
  join fetch b.author
  where lower(b.title) like lower(concat('%', :text, '%'))
  order by b.publishedOn desc
  """)
List<Book> search(@Param("text") String text);
JPQL ≠ SQL

Operujemy na encjach i polach

Book to nazwa encji, a b.author to pole obiektu. Hibernate dopiero tłumaczy JPQL na SQL konkretnej bazy.

20 // JPQL VS NATIVE SQL

Native query daje kontrolę kosztem przenośności

JPQL

  • odwołuje się do encji,
  • jest niezależne od dialektu,
  • współpracuje z mapowaniem ORM.

Native SQL

  • odwołuje się do tabel,
  • udostępnia funkcje PostgreSQL,
  • może wymagać jawnego countQuery.
Spring Data 4: można użyć @NativeQuery; klasyczne @Query(nativeQuery = true) również jasno komunikuje intencję.
21 // ZAPYTANIE NAZWANE

Book.java + BookRepository.java
@Entity

  name = "Book.findPublished",
  query = "select b from Book b " +
          "where b.published = true")
class Book { ... }

interface BookRepository
    extends JpaRepository<Book, Long> {
  List<Book> findPublished();
}
KONWENCJA NAZWY

Encja.metodaRepozytorium

Spring Data najpierw szuka Book.findPublished. @Query na metodzie ma pierwszeństwo przed named query.

23 // GRANICA OPERACJI

Transakcję zwykle wyznacza metoda serwisu

LibraryService.java
@Transactional
public Book publish(Long id) {
  Book book = repository.findById(id)
      .orElseThrow();
  book.publish();
  return book;
}

W kontekście trwałości Hibernate śledzi zmiany encji. Przy zatwierdzeniu transakcji wykonuje dirty checking i generuje UPDATE.

Nie zawsze potrzebujesz save: zarządzana encja zmieniona wewnątrz transakcji zostanie zsynchronizowana.
